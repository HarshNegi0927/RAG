# RAG Pipeline with Hybrid Search — Internal Docs

A retrieval-augmented generation system over a company's internal engineering
docs: dense + sparse (BM25) hybrid retrieval fused with RRF, evaluated
against a hand-written golden question set rather than eyeballed.

**Status: retrieval layer is built, tested, and measured. Generation
(the actual LLM answer + citations) is wired but not live-tested in this
environment — see "What's not done yet" below.**

## Why this exists

Every RAG tutorial builds dense-only search over one PDF and calls it done.
This repo exists to answer a narrower, more honest question: *does hybrid
search actually beat either method alone, on a real (if synthetic) internal
docs corpus, measured — not assumed?* The answer turned out to be more
interesting than "yes, obviously." See **Findings** below.

## Corpus

`data/raw/` contains 10 markdown docs simulating a fictional SaaS company's
("Loopstack") internal engineering wiki — deployment, incidents, auth,
migrations, onboarding, architecture, code review, feature flags, data
retention, monitoring. ~2,900 words total, 10 docs, deliberately written
with a mix of exact identifiers (env var names, function names, error
codes) and content that requires paraphrase understanding, so retrieval
quality differences between methods actually show up.

## Architecture

```
data/raw/*.md
      │
      ▼
 src/ingest.py ──────► two switchable chunking strategies:
      │                  - fixed        (naive fixed-size + overlap)
      │                  - structure_aware (splits on markdown headings first)
      ▼
 src/embeddings.py ──► pluggable embedder:
      │                  - spacy_local (default: free, offline, 300-dim word vectors)
      │                  - openai      (production: text-embedding-3-small, needs API key)
      ▼
 src/sparse_index.py (BM25)     src/retrieval.py (dense cosine + RRF fusion)
      │                                  │
      └──────────────┬───────────────────┘
                      ▼
            HybridRetriever.hybrid(query)
                      │
                      ▼
         src/generate.py  (Claude/GPT — grounded answer + citations)
              NOT YET LIVE-TESTED, see below
```

## Setup

```bash
pip install -r requirements.txt
python3 -m spacy download en_core_web_md
cp .env.example .env    # then edit .env and add your real GROQ_API_KEY
```

`config.py` loads `.env` automatically (via `python-dotenv`) — no manual
`export`/`$env:` needed once it's filled in. `.env` is gitignored; only
`.env.example` (no real secrets) is meant to be committed.

```bash
export PYTHONPATH=src   # Windows PowerShell: $env:PYTHONPATH="src"

python3 src/build_index.py                    # builds + persists the index
python3 scripts/compare_retrieval.py           # qualitative: dense vs sparse vs hybrid, 5 queries
python3 scripts/run_retrieval_eval.py          # quantitative: full 49-question golden eval
python3 scripts/tune_rrf_weight.py             # sweeps fusion weight, finds the best one
python3 scripts/compare_chunking.py            # fixed vs structure-aware chunking, head to head
python3 scripts/test_generation.py             # live grounded generation, needs GROQ_API_KEY in .env
```

Windows: `RUNME.ps1` runs everything above except generation in one go.
Linux/Mac/WSL: `RUNME.sh` does the same.

## Eval set

`eval/golden_qa.json` — 49 hand-written question/expected-source pairs,
built from the actual doc content (not generated by an LLM, per the point
of a golden set): 42 single-doc questions across all 10 docs tagged by
difficulty (`easy` / `medium` / `hard`) and kind (`identifier` — exact
term should be findable, `paraphrase` — deliberately avoids the doc's
wording), 2 multi-hop questions requiring two docs, and 5 deliberately
**unanswerable** questions (nothing in the corpus addresses them — these
matter later for testing "the system says it doesn't know" instead of
hallucinating, once generation is wired up).

## Findings (measured on this corpus, this embedder, top-5)

### Headline retrieval numbers

| Method | Hit@5 | MRR |
|---|---|---|
| Dense only (local embedder) | 68.2% | 0.563 |
| Sparse only (BM25) | **95.5%** | **0.824** |
| Hybrid (tuned weight) | 95.5% | 0.774 |

### 1. Found and fixed a real bug: embedding space collapse

Naively averaging spaCy's per-token word vectors (`doc.vector`, the
default) produced a **collapsed embedding space** — unrelated chunk pairs
averaged **0.79 cosine similarity** corpus-wide, meaning almost everything
looked similar to almost everything. One generic chunk ("Correctness
matters more than style...") became a "hub" that dense search returned as
the top hit for completely unrelated queries (billing services, data
retention) because it was full of common connective language that dominates
a naive average. This is a known failure mode of mean-pooled static word
vectors, not a spaCy-specific bug.

**Fix:** IDF-weighted pooling (common words contribute less, rare/technical
terms contribute more) + mean-centering (subtract the corpus's average
vector before normalizing — a simplified version of the top-component-
removal trick from the SIF sentence-embedding paper). Result: corpus-wide
average similarity went from **0.79 → -0.005**, and the hub effect
disappeared. See the docstring on `SpacyLocalEmbedder` in
`src/embeddings.py` for the full explanation.

### 2. Equal-weighted hybrid fusion measurably *underperformed* sparse-only

The obvious assumption — "hybrid should beat either method alone" — was
**not true** on this corpus with the free local embedder, even after fixing
the bug above. At the standard 50/50 RRF weighting, hybrid scored 88.6%
Hit@5 versus sparse-alone's 95.5%. A weak dense signal, fused at equal
weight with a strong sparse signal, actively dragged the fused ranking
down on several queries.

**Response:** made the RRF fusion weight configurable
(`reciprocal_rank_fusion(..., weights=[...])`) and swept it against the
golden set (`scripts/tune_rrf_weight.py`) instead of assuming a weight.
0.3 dense / 0.7 sparse ties sparse-only on Hit@5 while keeping the fusion
path meaningfully exercised — set as the new default in `config.py`.
**This weight is tuned for the weak local embedder specifically** and is
expected to need re-tuning (likely toward more dense weight) once
`EMBEDDING_PROVIDER=openai` is used — the config comment flags this
explicitly so it doesn't get silently stale.

Hybrid still has a real, specific win on this eval set worth naming: for
*"What services are involved when a customer gets billed?"* — a query with
no exact keyword overlap and no single strong semantic match — dense alone
ranked the right doc #3, sparse alone ranked it #5, and hybrid fused them
to #1. Aggregate metrics mostly reward sparse here; this is the query type
hybrid actually exists for.

### 3. Structure-aware chunking did not beat fixed-size chunking here

| Strategy | Chunks | Dense Hit@5 | Sparse Hit@5 | Hybrid Hit@5 |
|---|---|---|---|---|
| Fixed (800 char + overlap) | 31 | 77.3% | 93.2% | **97.7%** |
| Structure-aware (by heading) | 63 | 68.2% | 95.5% | 95.5% |

Counter to the naive expectation ("respecting document structure should
obviously retrieve better"), structure-aware chunking edged out slightly
*worse* on hybrid Hit@5 here. Likely explanation: splitting on every
heading in short, list-heavy internal docs produced much smaller chunks
(avg ~300 chars vs ~721 for fixed) with less surrounding context per
chunk — which starves the already-weaker local embedder in particular.
This isn't a verdict that structure-aware chunking is wrong in general;
it's a signal that `MAX_SECTION_CHARS` in `config.py` (currently 1200,
producing many chunks well under that cap because sections are short) is
a real tuning knob, and that chunk size interacts with embedder quality,
not just document layout. Worth re-testing after switching embedders
before drawing a final conclusion.

## Design decisions worth defending in an interview

- **Vector store is plain numpy, not ChromaDB/Qdrant.** At this corpus
  size (63 chunks), an exact brute-force cosine search is microseconds —
  an approximate index would add complexity with no benefit. `DenseIndex`
  is behind a narrow interface specifically so swapping in Chroma/Qdrant
  for a larger, persistent corpus is a one-file change.
- **Default embedder is local/free (spaCy word vectors), not OpenAI.**
  So the repo runs end to end for anyone who clones it, with zero API
  cost and zero setup friction — and so eval results in this README are
  reproducible by anyone, not gated behind a paid key. `EMBEDDING_PROVIDER=openai`
  is a one-line swap for production use.
- **RRF over score-based fusion.** BM25 scores and cosine similarities
  live on incomparable scales; fusing by rank position sidesteps that
  entirely. The tradeoff (see Finding #2) is that RRF still needs a
  trustworthy signal on *both* sides to earn its keep — it's not free
  insurance against a weak embedder.

## What's not done yet

- **Generation + citations** (`src/generate.py`) — **built and live-tested**,
  running on Groq (`openai/gpt-oss-120b`). Confirmed working: factually
  correct grounded answers, and the unanswerable test question ("what's
  our revenue last quarter") was correctly declined instead of
  hallucinated, with zero extra confidence-threshold logic. One real bug
  found and fixed in this pass: the model sometimes cites using full-width
  brackets (`【1】`) instead of the ASCII `[1]` the prompt asks for — the
  parser now normalizes known bracket variants before parsing, and the
  prompt explicitly forbids non-ASCII brackets as a second line of
  defense. Neither `api.groq.com` nor `api.x.ai` is reachable from the
  build sandbox itself (both confirmed `host_not_allowed`), so this was
  live-verified on a real Windows machine, not in-sandbox.
- **Citation verification** (`src/verify.py`) — **built**, not yet
  live-tested (same network limitation as generation). Splits an answer
  into per-sentence claims, resolves each claim's citation(s) to their
  actual chunk text, and asks an LLM judge whether the cited passage(s)
  genuinely support the claim (`SUPPORTED` / `PARTIAL` / `UNSUPPORTED`),
  rather than only checking that a citation number resolves to *some*
  real chunk. Claim-splitting was tested against the real answers from
  the live generation run above — including the interesting 5-citation
  case (`[1][2][3][4][5]`, all cited to support one "the docs don't
  mention this" claim), which split and resolved correctly. One bug found
  and fixed in that testing: the sentence-splitter initially missed every
  citation immediately followed by a period (`...incident[1].` — the
  common case) because it only matched citations at the exact end of a
  sentence with nothing after them. Run
  `scripts/test_verification.py` to see real verdicts against your live
  Groq output.
- **Confidence scoring** (`src/confidence.py`) — **built and measured**
  against the full golden set. Key finding: the hybrid RRF score is
  useless for this (answerable vs. unanswerable score distributions fully
  overlapped, 0.011–0.016 both). Raw top-1 BM25 score, taken *before*
  fusion, does separate them — at threshold 8.0, it catches **5/5**
  unanswerable golden questions, at the cost of wrongly flagging **2/44**
  genuinely answerable ones (`priv-02`, `priv-03` — both phrased in a way
  that shares little vocabulary with their own answer). That's a real,
  measured tradeoff, not an assumed one — see
  `scripts/tune_confidence_threshold.py`. The gate is a separate,
  composable pre-check (`confidence.py`, not baked into `generate.py`) so
  it can skip the LLM call entirely for low-confidence questions —
  confirmed working with `GROQ_API_KEY` unset entirely (see
  `scripts/test_confidence_gate.py`), which is a real cost saving, not
  just a nicer-sounding refusal.
- **`scripts/run_full_eval.py`** — the other eval scripts each measure one
  layer (retrieval quality, chunking strategy, RRF weight) in isolation;
  this one runs the *whole* stack — confidence gate → generation →
  citation verification → answer-correctness judging against the golden
  set's notes — on a stratified 14-question sample (2 easy, 2 medium, all
  5 hard/multi-hop, all 5 unanswerable) and produces one consolidated
  report. Needs `GROQ_API_KEY`; not run yet in this session.
- **Cross-encoder reranker** on top of the fused top-20.
- **FastAPI service + dashboard + Docker packaging.**

## A note on cross-platform reproducibility

The eval numbers above were generated on Linux; re-running the identical
scripts on Windows reproduced the **aggregate** Hit@5/MRR numbers exactly
in the weight sweep and chunking comparison, but shuffled a couple of
individual near-tied rankings in the qualitative 5-query demo and the
per-difficulty/per-kind eval breakdown (aggregate counts stayed the same,
which specific borderline queries flipped did not). Sparse/BM25 results
were identical bit-for-bit across both runs; only dense/hybrid (which
involve floating-point cosine similarity) showed any drift. Most likely
cause: different BLAS backends between platforms produce tiny
floating-point differences in vector math, occasionally enough to flip a
near-tied ranking. Doesn't change any of the findings above, but worth
knowing before quoting per-query results as if they're bit-exact across
machines.
